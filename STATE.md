## Security

Grade: **A** (review 2026-11-07 r2, rubric: A = no open Medium or higher, every open Low documented with a reason). No open Critical, High or Medium. Fixed in r2: M1 (the D-004 alert let a malicious cask through; now an exact template match plus a provenance audit of every push, D-005) and L1 (state-guard merges-only escape, #8). Not A+ because these Lows stay open by design:

- L2, Accepted risk (D-002, D-004): the write deploy key `HOMEBREW_TAP_DEPLOY_KEY` can push any file to `main`, so a stolen key could ship a changed cask to every `brew upgrade`. Push rulesets that would limit it to `Casks/**` exist only for organization-owned repos, and required checks would break the release job. Mitigations: the key sits in an isolated `permissions: {}` job; after every push the `tests` workflow requires the cask to equal the release template (exact URL, no extra stanzas) and `push-audit` requires every commit to be a GitHub-merged PR or a clean bot bump; on failure the `alert` job opens an issue. Rotate the key by 2027-09-27 (created 2026-09-27; record the new date here when done).
- L4, Accepted risk (D-005): those checks run from the pushed commit, so a push that also rewrites `.github/workflows/tests.yml`, `tests/` or `scripts/` can disable them. Not fixable inside this personal-account repo (no push rulesets). Next step if wanted: a watcher outside the repo (homelab job or a scheduled workflow in a repo the key cannot write) that runs a trusted copy of `scripts/audit-push.sh` against `main`.
- L3, Accepted risk (D-003): `main` requires no PR review or status checks, only no force-push and no deletion, because the release job pushes directly.
- Operator-only (blocked, optional): confirm GitHub notification settings send Actions failure emails for this repo, as a second channel next to the alert issue.
